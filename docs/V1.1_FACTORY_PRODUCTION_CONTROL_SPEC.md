# FactoryOps V1.1 — Factory Production Control

**Status:** Phase 0 — Specification & Architecture (no code implemented)
**Milestone:** V1.1 Factory Production Control
**Predecessor:** V1 Foundation (M1–M4A) — materials, stock, batches, additions, operator capture, production runs, output, consumption
**Successor:** V1.2 Reconciliation → V2 Intelligence (AI Factory Operations Foreperson)

> This document is a proposal for review and approval. It intentionally contains
> **no implementation**. It records what exists today, what V1.1 adds, and exactly
> how to extend the current system without rebuilding it or breaking historical data.

Related documents: [Architecture](architecture.md) · [ERD](erd.md) · [System health](system-health.md) · [Setup](setup.md)

## 1. Purpose

Build a controlled production workflow for sanitary-pad manufacturing so FactoryOps can answer, for any production run:

> **What are we producing, in what variant and packaging, what did the operator record, what should the quantity be, what did QC verify, and where is there a discrepancy?**

V1.1 turns FactoryOps from a capture system into a system that **enforces the factory's production logic** while preserving the original operator data and making every correction auditable.

The milestone delivers ten capabilities:

1. Product variants (configurable, not hardcoded)
2. Packaging relationships (data-driven conversion)
3. Required-field gates (server-enforced)
4. Production-stage workflow (a real state machine)
5. QC permissions (deliberately restricted)
6. QC photos (attached to the QC record, via media storage)
7. QC finished goods (verified quantity)
8. Expected vs recorded quantities (three distinct values)
9. NB! variance engine (a reusable, deterministic domain service)
10. Audit trail (WHO / WHAT / WHEN / OLD / NEW / WHY)

**Core principle carried from V1:** never overwrite an operator's original record. "Auto-correct" means *calculate the expected value and identify the discrepancy*, not silently replace the operator's number. Any real correction produces an audit event.

## 2. Current-State Architecture Findings

All findings below were confirmed by inspecting the repository (not assumed from the brief).

### 2.1 Apps and layering

Modular monolith. Domain apps under `apps/`. Relevant apps: `accounts`, `factories`, `machines`, `materials`, `production`, `orders`, `dashboard`. Stubs (no models/migrations): `shifts`, `handovers`, `downtime`, `reports`.

Established layering pattern (V1.1 must follow it):

- **Models** (`apps/*/models.py`) — data + invariants. Every model overrides `clean()` for cross-factory validation and `save()` calls `full_clean()`.
- **Services** (`apps/*/services.py`) — deterministic calculations returning structured dicts (e.g. `apps/materials/services.py`, `apps/production/services.py`). `Decimal`, `ROUND_HALF_UP`, quantum `0.001`, UTC calendar-date windows.
- **Workflow** (`apps/*/workflow.py`) — transactional floor operations that create event rows (`apps/production/workflow.py`, `apps/materials/workflow.py`). Factory is always derived from `user.factory`, never from posted IDs. `select_for_update()` is used on runs.
- **Views** (`apps/dashboard/*_views.py`) — role-gated; delegate to forms/workflow; translate `ValidationError` to messages.
- **Permissions** (`apps/dashboard/permissions.py`) — role tuples + `role_required` decorator.

### 2.2 Roles

`apps/accounts/models.py` defines `Role`: `ADMIN`, `SUPERVISOR`, `OPERATOR`, `QC`. `User` has `role`, `employee_id` (unique/nullable), and `factory` (nullable FK, `SET_NULL`). Helper properties `is_admin/is_supervisor/is_operator/is_qc`.

`apps/dashboard/permissions.py` role tuples today:

| Tuple | Members |
|---|---|
| `OPERATOR_ROLES` | OPERATOR, QC, SUPERVISOR, ADMIN |
| `PRODUCTION_ROLES` | OPERATOR, SUPERVISOR, ADMIN |
| `SUPERVISOR_ROLES` | SUPERVISOR, ADMIN |
| `MANAGER_ROLES` / `EXECUTIVE_ROLES` | ADMIN |
| `INVENTORY_ROLES` | SUPERVISOR, ADMIN |

**Finding (important):** `QC` is in `OPERATOR_ROLES` (can *view* operator screens) but is **excluded from `PRODUCTION_ROLES`** and every other write path. Tests explicitly assert QC cannot start/complete runs, record output, material state, or consumption (`apps/production/test_operator_workflow.py::test_qc_cannot_start_or_complete_production`, `apps/production/test_material_state.py::test_qc_cannot_record_material_state`, `apps/materials/test_operator_consumption.py::test_qc_cannot_record_consumption`). **QC currently has no write capability at all.** V1.1 must grant QC a *scoped* write surface (its own verification records) without widening these existing operator/production paths — those tests must keep passing.

### 2.3 Production models (`apps/production/models.py`)

- **`ProductionRunStatus`** = `PLANNED`, `IN_PROGRESS`, `COMPLETED`, `CANCELLED`.
- **`ProductionRun`**: `factory` (PROTECT); `production_line`, `machine`, `created_by` all **nullable/blank** (to support admin-created/legacy runs); `reference`, `status` (default `PLANNED`), `started_at`, `ended_at`, `notes`, timestamps. Unique `(factory, reference)`. Check constraint links `ended_at`/`started_at`. `clean()` enforces status↔timestamp rules and same-factory line/machine. **`save()` calls `full_clean()`.**
- **`ProductionRunMaterialState`**: machine/spare roll snapshot per run/material.
- **`FinishedGood`**: `factory`, `code`, `name`, `is_active`. Unique `(factory, code)`.
- **`ProductionOutput`**: `production_run` (PROTECT); `output_name` (blank) **or** `finished_good` (nullable) — `clean()` requires at least one; `quantity` > 0; `recorded_at`. **No variant, packaging, or expected-quantity concept.**
- **`ProductionReject`**, plus finished-goods warehouse chain: `Warehouse`, `FinishedGoodStockRecord`, `FinishedGoodAddition`, `FinishedGoodAdjustment`, `FinishedGoodDispatch`, `FinishedGoodReconciliation`.

### 2.4 Materials models (`apps/materials/models.py`)

`UnitOfMeasure`, `MaterialCategory`, `Material`, `StockRecord`, `MaterialBatch`, `MaterialAddition`, `MaterialConsumption`, `MaterialWaste`, `MaterialScrap`, `StockReconciliation`.

**`MaterialConsumption` (the model the brief flagged):** `factory`, `material`, `quantity`>0, `consumed_at`, plus **optional** `production_reference` (free text), `production_run` (nullable FK), `batch` (nullable FK), `recorded_by` (nullable). Operator capture (`apps/materials/workflow.py`) requires `batch` and `production_run`, but the **model keeps them nullable** so historical M4 consumption rows (admin-created, no batch/run) remain valid. **V1.1 must not tighten these fields.**

### 2.5 Services (deterministic calculators — the template for the variance engine)

`apps/materials/services.py` and `apps/production/services.py` expose pure functions (`calculate_expected_closing`, `reconcile_*`) returning dicts with `Decimal` values quantised to `0.001`, `ROUND_HALF_UP`, UTC date windows. The variance engine must follow this exact shape and testability.

### 2.6 Capture surfaces (there are two, both must keep working)

1. **Django Admin** — supervisor/admin capture surface (per [architecture.md](architecture.md)); every production/material model is registered with `readonly` audit timestamps.
2. **Operator floor workflow** — `apps/dashboard/production_views.py` + `apps/dashboard/forms.py`: select line → start run (machine) → record output → record consumption / material state → complete. Gated by `OPERATOR_ROLES`/`PRODUCTION_ROLES`.

### 2.7 Media configuration

`config/settings/base.py` already sets `MEDIA_URL=/media/` and `MEDIA_ROOT=BASE_DIR/'media'`, and `config/urls.py` serves media in `DEBUG`. **However, Pillow is NOT installed** (`import PIL` fails; not in `requirements.txt`). This directly affects QC photos — see §12.

### 2.8 Test baseline

327 tests pass on `main` (see §22 for the per-file breakdown). `python manage.py makemigrations --check` reports exactly one pre-existing drift, `accounts.0002_alter_user_managers` (managers change). Per the brief this is **out of scope** and must be left untouched and reported.

## 3. Domain Model Proposal

V1.1 adds three concept clusters. New models are shown with their home app.

```text
CATALOG (new app: apps.catalog) — factory product master data
   Product
     └── ProductVariant
   Packaging
     └── (self-referential composition → conversion engine)

PRODUCTION (extend existing apps.production)
   ProductionRun                      (extend: + stage, + config FKs, all nullable)
     ├── ProductionOutput             (existing; optionally + variant/packaging refs)
     ├── MaterialConsumption          (existing, unchanged)
     └── QCVerification (new)         (OneToOne with ProductionRun)
            └── QCPhoto (new)

AUDIT (new app: apps.audit)
   AuditEvent                         (append-only; generic target)
```

Design rules applied to every new model (mirroring the codebase):

- Carry `factory` (directly or via a parent) and validate same-factory relationships in `clean()`.
- `Decimal(max_digits=12, decimal_places=3)` for quantities; `MinValueValidator`.
- `created_at`/`updated_at` timestamps; append-only where the brief requires history.
- New fields on **existing** models are **nullable/blank** so legacy rows and `full_clean()` on `save()` are unaffected (see §19–§21).

### App-placement decision

- **New app `apps.catalog`** for `Product`, `ProductVariant`, `Packaging` (and the packaging composition). Rationale: these are reusable factory master data, not production events; a dedicated app keeps `apps.production` focused and matches the existing "one domain per app" convention. *Alternative considered:* placing them in `apps.production` (fewer apps, but muddies production events with master data). Recommendation: `apps.catalog`.
- **QC lives in `apps.production`** (`QCVerification`, `QCPhoto`) because it is tightly bound to `ProductionRun` and its factory scope.
- **New app `apps.audit`** for `AuditEvent`. Rationale: cross-cutting; V1.2 reconciliation and V2 AI will also want to read/write audit history. *Alternative:* a production-scoped `ProductionAuditEvent` (simpler, but not reusable). Recommendation: `apps.audit` with a generic target.

## 4. Product / Variant Design

Configurable data — **never hardcoded** (`if variant == "Maxi's"` is prohibited).

**`apps.catalog.Product`**

| Field | Type | Notes |
|---|---|---|
| `factory` | FK → factories.Factory (PROTECT) | factory-scoped |
| `code` | Char(50) | unique per factory |
| `name` | Char(150) | e.g. "Sanitary Pads" |
| `is_active` | Bool | default True |
| timestamps | | |

Constraint: `UniqueConstraint(factory, code)`. `clean()`: strip code/name; block creation for inactive factory (mirrors `FinishedGood`).

**`apps.catalog.ProductVariant`**

| Field | Type | Notes |
|---|---|---|
| `product` | FK → Product (PROTECT) | |
| `code` | Char(50) | unique per product |
| `name` | Char(100) | e.g. "Standard Length", "Thins", "Extra Length", "Maxi's" |
| `is_active` | Bool | default True |
| timestamps | | |

Constraint: `UniqueConstraint(product, code)`. `clean()`: variant inherits factory via `product.factory` (validated wherever a variant is attached to a run).

Initial seed data (Sanitary Pads → the four variants) is supplied via a **data migration or admin entry**, not application logic. Another factory can define entirely different products/variants without code changes.

**Optional link to `FinishedGood`:** a `ProductVariant` MAY carry a nullable FK to an existing `FinishedGood` so produced output can flow into the existing finished-goods warehouse chain in V1.2. Not required for V1.1; keep nullable.

## 5. Packaging Relationship Design

The heart of the "reusable calculation engine". Packaging conversions are **data**, resolved by a service — no `if packaging == "15's"` anywhere.

### Model: `apps.catalog.Packaging`

| Field | Type | Notes |
|---|---|---|
| `factory` | FK → factories.Factory (PROTECT) | factory-scoped |
| `code` | Char(50) | e.g. "10's", "15's", "60's"; unique per factory |
| `name` | Char(100) | human label |
| `contains` | self-FK (nullable, PROTECT) | the packaging this one is composed of; null ⇒ base pack |
| `quantity_per` | Decimal(12,3) > 0 | how many of `contains` are in one of this packaging |
| `base_unit_quantity` | Decimal(12,3) > 0, nullable | individual units in a **base** pack; required iff `contains` is null |
| `individual_unit_label` | Char(50) | e.g. "pads" (display only) |
| `is_active` | Bool | |
| timestamps | | |

Modeling the brief's table:

```text
10's : contains = null, base_unit_quantity = 10          → 10 individual pads   (base)
15's : contains = 10's, quantity_per = 15                 → 15 × 10 = 150 pads
60's : contains = 10's, quantity_per = 60                 → 60 × 10 = 600 pads
```

### Invariants (enforced in `clean()`)

- If `contains` is null ⇒ `base_unit_quantity` **required**, `quantity_per` ignored/1.
- If `contains` is set ⇒ `quantity_per` **required**, `base_unit_quantity` must be null.
- `contains` must belong to the **same factory**.
- **No cycles** (a packaging cannot contain itself directly or transitively) — validated by walking the chain with a visited-set and a max-depth guard.
- `UniqueConstraint(factory, code)`.

### Conversion engine (service — see §15)

`apps.catalog.services.individual_units(packaging) -> Decimal`:

```text
if packaging.contains is None:
    return base_unit_quantity
return quantity_per * individual_units(packaging.contains)   # memoised, cycle-guarded
```

This single deterministic function powers all expected-quantity math. It is the only place that knows how packs convert to individual units.

## 6. ProductionRun Integration

**Extend, do not replace, the existing `ProductionRun`.** All additions are nullable so legacy/admin runs and `full_clean()` remain valid.

New fields on `apps.production.ProductionRun` (all nullable/blank):

| Field | Type | Purpose |
|---|---|---|
| `product` | FK → catalog.Product (PROTECT, null) | production configuration |
| `variant` | FK → catalog.ProductVariant (PROTECT, null) | |
| `packaging` | FK → catalog.Packaging (PROTECT, null) | drives expected qty |
| `planned_pack_quantity` | Decimal(12,3), null | the "20" in "20 × 15's" |
| `stage` | Char(30), choices=`ProductionStage`, null | V1.1 state machine (see §8) |

`clean()` additions (only when the fields are set — never forcing them on legacy rows):

- `variant.product_id == product_id`.
- `product.factory_id == packaging.factory_id == run.factory_id`.
- Existing line/machine same-factory checks are unchanged.

**Why a new `stage` field instead of reusing `status`:** `status` (`PLANNED/IN_PROGRESS/COMPLETED/CANCELLED`) is load-bearing — it is referenced by the operator workflow, model check logic, and ~40 tests. Overloading it with eight new states would break them. `stage` is an **additive, parallel** field; legacy runs have `stage = null` and are treated as "legacy" (see §20). A mapping helper keeps `status` and `stage` consistent for new runs (§8).

`ProductionOutput` (optional, nullable): may gain `variant`/`packaging` FKs to record what a specific output line represents. Not required for V1.1 if the run-level config is sufficient; recommend keeping run-level config authoritative and leaving `ProductionOutput` unchanged in V1.1-A/B, revisiting in V1.1-D.

## 7. Required-Field Matrix

Requirements are **enforced server-side** in the state-transition service (§8), never by disabled buttons/JS alone. The UI *may* show "you still need to complete these N fields" by calling the same read-only gate checker.

| Target stage | Preconditions that must be satisfied to enter it |
|---|---|
| `DRAFT` | Run exists with `factory`. (Entry state for V1.1 runs.) |
| `INPUTS_COMPLETE` | `product`, `variant`, `packaging`, `production_line`, `machine` all set and same-factory; `planned_pack_quantity` > 0. |
| `PRODUCTION_ACTIVE` | Inputs complete **and** `started_at` set; `status → IN_PROGRESS`. (Reuses existing `start_production_run`.) |
| `OUTPUT_RECORDED` | ≥ 1 `ProductionOutput` for the run (operator-recorded quantity present). |
| `QC_REQUIRED` | Output recorded and run submitted to QC by the operator. |
| `QC_COMPLETE` | A `QCVerification` exists with: confirmed `variant` + `packaging`, ≥ 1 `QCPhoto` (policy-configurable minimum), `qc_verified_quantity` set, and QC marked it verified. |
| `VALIDATION` | Variance engine has computed expected vs recorded vs verified (a structured result exists). |
| `COMPLETED` | No unresolved blocking exception (variance within tolerance **or** an authorised correction/override with an audit event). `status → COMPLETED`, `ended_at` set. |
| `EXCEPTION` | Reachable from `VALIDATION` when variance exceeds tolerance; requires supervisor/admin resolution (§16). |

Gate checker contract: `gate_requirements(run, target_stage) -> {"ok": bool, "missing": [human-readable strings]}` — pure, read-only, reused by both the API/view and the transition enforcer.

> The matrix is a **proposal**. During V1.1-B implementation, validate each mandatory field against real pilot data before enforcing, so we do not accidentally block legitimate runs.

## 8. Production State Machine

New `apps.production.ProductionStage` (`TextChoices`): `DRAFT`, `INPUTS_COMPLETE`, `PRODUCTION_ACTIVE`, `OUTPUT_RECORDED`, `QC_REQUIRED`, `QC_COMPLETE`, `VALIDATION`, `COMPLETED`, `EXCEPTION`, `CANCELLED`.

Allowed transitions (enforced in `apps/production/state_machine.py`, a new service module):

```text
DRAFT           → INPUTS_COMPLETE | CANCELLED
INPUTS_COMPLETE → PRODUCTION_ACTIVE | DRAFT | CANCELLED
PRODUCTION_ACTIVE → OUTPUT_RECORDED | CANCELLED
OUTPUT_RECORDED → QC_REQUIRED | CANCELLED
QC_REQUIRED     → QC_COMPLETE                     (QC only)
QC_COMPLETE     → VALIDATION
VALIDATION      → COMPLETED | EXCEPTION
EXCEPTION       → VALIDATION | COMPLETED          (supervisor/admin, with audit)
```

Rules:

- Each transition function checks (a) the caller's role, (b) the target is reachable from the current stage, (c) `gate_requirements` is satisfied. On success it updates `stage` inside a `transaction.atomic()` with `select_for_update()` (matching existing workflow) and writes an `AuditEvent` for stage changes.
- **`status` ↔ `stage` mapping** for new runs: entering `PRODUCTION_ACTIVE` sets `status=IN_PROGRESS`; entering `COMPLETED` sets `status=COMPLETED`; `CANCELLED` stage ⇒ `status=CANCELLED`. This keeps existing status-based dashboards and constraints correct.
- **Legacy runs** (`stage=null`) are never forced into the machine; they render as "Legacy" and are read-only in the V1.1 workflow (§20).
- Enforcement is server-side only. The UI reflects state but cannot authorise a transition.

## 9. Operator Permissions

Operator (role `OPERATOR`; and by inclusion SUPERVISOR/ADMIN via `PRODUCTION_ROLES`) **can**:

- Configure a run (product/variant/packaging/line/machine) up to `INPUTS_COMPLETE`.
- Start production, record production activity, record output (operator-recorded quantity), record consumption and material state (existing paths, unchanged).
- Submit a run for QC (`OUTPUT_RECORDED → QC_REQUIRED`).
- View their own/factory production history.

Operator **cannot**:

- Create, edit, or complete a `QCVerification`; upload QC photos; set `qc_verified_quantity`.
- Advance `QC_REQUIRED → QC_COMPLETE` or beyond.
- Silently modify original production records (corrections go through the audited supervisor path).

Implementation: keep the existing `PRODUCTION_ROLES` write paths as-is (protects current tests). Add new operator-only transition endpoints for run configuration and "submit for QC", gated by `PRODUCTION_ROLES` and by the state machine.

## 10. QC Permissions

Introduce a scoped QC capability **without** widening operator/production write paths. Add a new role tuple `QC_ROLES = (QC, SUPERVISOR, ADMIN)` in `apps/dashboard/permissions.py` and a helper `can_perform_qc(user)`.

QC (role `QC`) **can**:

- Open runs in `QC_REQUIRED` for its factory.
- Confirm/select the `variant` and `packaging` relationship on the `QCVerification`.
- Upload QC photos.
- Record total finished goods (`qc_verified_quantity`).
- Complete QC verification (`QC_REQUIRED → QC_COMPLETE`).
- See expected vs recorded vs verified values (read-only, from the variance engine).

QC **cannot**:

- Edit the operator's original `ProductionOutput`/`ProductionRun` inputs or `MaterialConsumption`.
- Start/complete production runs, record output/material state/consumption (existing negative tests must stay green).
- Act as an unrestricted production administrator.

**Backward-compatibility note:** QC remains in `OPERATOR_ROLES` (view access) and remains **excluded** from `PRODUCTION_ROLES`. The only new QC power is over QC records. This satisfies the existing "QC cannot record production/consumption/material state" tests unchanged.

## 11. Supervisor / Admin Permissions

Supervisor (`SUPERVISOR`) and Admin (`ADMIN`) **can**:

- Everything operators and QC can do (they are already members of the relevant tuples).
- Investigate discrepancies; view the full variance breakdown and audit history.
- Perform **controlled corrections** to production/QC values — but only via an audited correction service that preserves the original value and requires a reason (§16, §17).
- Resolve `EXCEPTION` runs (`EXCEPTION → VALIDATION/COMPLETED`).

Admin additionally **controls configuration**: manage `Product`, `ProductVariant`, `Packaging` (via Admin and/or a config UI). Configuration changes are factory-scoped.

Separation of duties:

```text
OPERATOR  → produces / records          (authoritative source data, never silently changed)
QC        → verifies                    (own records + photos + verified qty)
SUPERVISOR→ resolves exceptions         (audited corrections)
ADMIN     → controls configuration      (catalog master data)
```

## 12. QC Photo Architecture

Photos belong to the **QC verification context**, not dumped on the run.

**`apps.production.QCPhoto`**

| Field | Type | Notes |
|---|---|---|
| `qc_verification` | FK → QCVerification (CASCADE) | ownership |
| `image` | `FileField` (recommended) or `ImageField` | stored via Django media storage (`MEDIA_ROOT`) |
| `caption` | Char(200), blank | optional |
| `uploaded_by` | FK → user (SET_NULL, null) | set server-side |
| `uploaded_at` | DateTime(default=now) | |
| timestamps | | |

Context is always recoverable: `factory` and `production_run` via `qc_verification.production_run.factory`; `uploaded_by`, `uploaded_at` on the row. The **database stores only the file reference/metadata**, never the binary.

Upload path: a per-factory/run `upload_to` callable, e.g. `qc/<factory_id>/<run_id>/<uuid>.<ext>`, to keep media organised and factory-scoped.

Validation (server-side): allowed extensions (`.jpg/.jpeg/.png/.webp`), max file size, and content-type check.

### Pillow decision (must be made before V1.1-C)

`ImageField` **requires Pillow, which is not currently installed** (confirmed: `import PIL` fails; absent from `requirements.txt`).

- **Recommended:** use `FileField` + explicit extension/size/content validators. **Zero new dependencies**, satisfies "store via media storage, not binary in DB", and keeps parity with the brief.
- **Alternative:** add `Pillow` to `requirements.txt` and use `ImageField` (gives image-dimension validation and guarantees the upload is a real image). This is the one dependency V1.1 might justify; call it out explicitly for approval rather than adding silently.

Either way, no image binaries in the database.

## 13. Finished-Goods (QC) Architecture

Three distinct quantities are stored and **never conflated**, all normalised to **individual units (pads)** via the packaging engine while preserving raw entries:

| Value | Source | Field (on `QCVerification`) |
|---|---|---|
| **Expected** | Computed: `planned_pack_quantity × individual_units(packaging)` | `expected_quantity` (derived, stored at compute time) |
| **Operator recorded** | What the operator entered (preserved verbatim) | `recorded_quantity` (copied/linked from operator output) |
| **QC verified** | What QC physically confirms | `qc_verified_quantity` (QC-entered) |

Worked example (`20 × 15's`):

```text
individual_units(15's) = 15 × individual_units(10's) = 15 × 10 = 150
EXPECTED        = 20 × 150 = 3,000
OPERATOR RECORDED = 3,400        (preserved — never overwritten)
QC VERIFIED     = 3,000
VARIANCE        = +400 recorded vs expected ; 0 QC vs expected
```

`QCVerification` (new, `OneToOneField(ProductionRun)`):

| Field | Type | Notes |
|---|---|---|
| `production_run` | OneToOne → ProductionRun (PROTECT) | one QC record per run |
| `variant` | FK → catalog.ProductVariant (PROTECT, null) | QC-confirmed |
| `packaging` | FK → catalog.Packaging (PROTECT, null) | QC-confirmed |
| `expected_quantity` | Decimal(12,3), null | derived; stored when computed |
| `recorded_quantity` | Decimal(12,3), null | operator's value, preserved |
| `qc_verified_quantity` | Decimal(12,3), null | QC entry |
| `status` | Char, choices (`PENDING`/`VERIFIED`/`EXCEPTION`) | |
| `verified_by` | FK → user (SET_NULL, null) | |
| `verified_at` | DateTime, null | |
| timestamps | | |

`clean()`: same-factory checks (variant/packaging/run share a factory); quantities ≥ 0; QC verified quantity may equal, exceed, or fall below expected — the engine, not `clean()`, decides exception status.

## 14. Expected Quantity Calculation Rules

Deterministic, decimal, and defined once:

1. `individual_units(packaging)` resolves packs → individual units through the `contains` chain (§5).
2. `expected_individual_units(run) = run.planned_pack_quantity × individual_units(run.packaging)`.
3. Quantities use `Decimal`, quantised to `0.001`, `ROUND_HALF_UP` (matching `apps/materials/services.py`).
4. If configuration is incomplete (no packaging or no `planned_pack_quantity`), expected is **undefined** (return `None`) — never guess.
5. Expected is **computed**, then **stored** on `QCVerification.expected_quantity` at validation time for audit stability; recomputation must be idempotent.
6. Units of comparison: expected, recorded, and verified are all expressed in **individual units** so variance is apples-to-apples. Raw pack counts remain on the run.

## 15. Variance Engine Design

A reusable, deterministic **domain service** — not logic in views or templates. New module `apps/production/variance.py` (calculation) mirroring the existing services' style; consumed by views, QC screens, and the future AI Foreperson.

Signature (pure, no DB writes):

```text
compute_variance(expected: Decimal|None,
                 recorded: Decimal|None,
                 qc_verified: Decimal|None,
                 *, tolerance_pct: Decimal = FACTORY_DEFAULT) -> VarianceResult
```

`VarianceResult` (a frozen dataclass or plain dict, JSON-serialisable for AI):

| Key | Meaning |
|---|---|
| `expected` | echoed input (or None) |
| `recorded` | echoed input (or None) |
| `qc_verified` | echoed input (or None) |
| `recorded_vs_expected` | `recorded − expected` (None if either missing) |
| `qc_vs_expected` | `qc_verified − expected` |
| `qc_vs_recorded` | `qc_verified − recorded` |
| `recorded_vs_expected_pct` | percentage where `expected > 0`, else None |
| `qc_vs_expected_pct` | percentage where `expected > 0`, else None |
| `status` | `OK` / `WITHIN_TOLERANCE` / `EXCEPTION` / `INSUFFICIENT_DATA` |

Rules:

- Deterministic and side-effect free; all `Decimal`; division guarded (no divide-by-zero; percentage only when `expected > 0`).
- `INSUFFICIENT_DATA` when a required input is `None`.
- `status = EXCEPTION` when the relevant absolute/percentage variance exceeds tolerance; `WITHIN_TOLERANCE` when non-zero but under tolerance; `OK` when zero.
- Tolerance is **configuration** (per-factory default, overridable per product/variant later) — not a magic number in code.
- A thin wrapper `variance_for_run(run)` reads the stored quantities and calls `compute_variance`, so callers never re-implement the math.

**"Auto-correct" means:** automatically compute expected and surface the discrepancy. It **never** means overwriting the operator's recorded value. Any actual value change is a §16/§17 controlled correction that emits an audit event.

---

## 16. Exception States

- A run whose variance `status = EXCEPTION` moves to (or is flagged for) the `EXCEPTION` stage at `VALIDATION`.
- `EXCEPTION` runs **cannot auto-complete**. Resolution requires SUPERVISOR/ADMIN action:
  - **Accept variance** (record an explanation) → `COMPLETED` with an audit event; original values preserved.
  - **Controlled correction** (§17) of a specific value with old/new/reason → recompute variance → `VALIDATION` → `COMPLETED` if resolved.
- `QCVerification.status` may independently be `EXCEPTION` to flag QC-vs-expected mismatches for review.
- No exception is ever resolved by silently editing source data.

## 17. Audit Trail Design

New app **`apps.audit`**, model **`AuditEvent`** (append-only; never edited or deleted):

| Field | Type | Notes |
|---|---|---|
| `factory` | FK → factories.Factory (PROTECT) | factory-scoped, filterable |
| `actor` | FK → user (SET_NULL, null) | WHO |
| `action` | Char(50) | WHAT, e.g. `STAGE_CHANGE`, `QC_VERIFIED`, `CORRECTION`, `EXCEPTION_ACCEPTED` |
| `target_content_type` / `target_object_id` | Generic FK | the affected record (run, QC, output) |
| `field_name` | Char(100), blank | field corrected, if any |
| `old_value` | Text, blank | previous value (string form) |
| `new_value` | Text, blank | new value |
| `reason` | Text, blank | WHY (required for corrections/exception resolution) |
| `created_at` | DateTime(auto_now_add) | WHEN |

Service `apps.audit.services.record_event(...)` is the single write path, called from the state machine and the correction service inside the same transaction as the change it records. Corrections use a helper `apply_controlled_correction(instance, field, new_value, *, actor, reason)` that reads the old value, applies the new value, saves, and emits the `AuditEvent` atomically — guaranteeing the original is captured before mutation.

Example captured event:

```text
actor: supervisor1
action: CORRECTION
target: ProductionRun PR-20260930-001 (QCVerification)
field: recorded_quantity        old: 3400   new: 3000
reason: "Packaging count mismatch confirmed during QC"
when: 2026-09-30 18:42 UTC
```

The operator's original `3,400` is **retained** — the correction is a new event, not an in-place erasure of history.

## 18. Factory Isolation Rules

Consistent with [architecture.md](architecture.md) principle 4:

- Every new model is factory-scoped (directly, or via `product`/`production_run`/`qc_verification`).
- `Product`, `ProductVariant`, `Packaging`, `QCVerification`, `QCPhoto`, `AuditEvent` all validate that related objects share one factory in `clean()`.
- All read querysets are filtered by `user.factory` (reuse `apps/dashboard/querysets.py::user_factory` and the `*_for(user)` helpers). Workflow derives factory from `user.factory`, never from posted IDs (existing rule).
- Uniqueness is scoped per factory (`(factory, code)`), matching existing masters.

## 19. Migration Strategy

- **Additive only.** New apps (`catalog`, `audit`) get initial migrations; `production` gets additive migrations for new nullable fields and the two new models.
- **Every new field on an existing model is `null=True, blank=True`** (`product`, `variant`, `packaging`, `planned_pack_quantity`, `stage`). This is mandatory because `ProductionRun.save()` calls `full_clean()`; non-nullable additions would break saving legacy runs and admin edits.
- Register `apps.catalog` and `apps.audit` in `INSTALLED_APPS`.
- Seed data (Sanitary Pads product, four variants, 10's/15's/60's packaging) via a **separate data migration** or admin fixture — factory-specific, not code.
- **Do not** create or modify `accounts.0002_alter_user_managers`; leave the known drift untouched (§21).
- One migration per logical step (catalog models → production fields → QC models → audit model), so review and rollback stay granular.

## 20. Backward Compatibility Strategy

- **Legacy `ProductionRun`** (null `line`/`machine`/`created_by`, `stage=null`, status-only): remains valid and editable in Admin; treated as "Legacy" in the V1.1 UI; excluded from state-machine enforcement. New V1.1 runs opt into `stage`.
- **`MaterialConsumption` stays as-is** — `production_run`, `batch`, `production_reference`, `recorded_by` remain nullable. V1.1 does **not** tighten these (protects historical M4 rows and `test_operator_consumption` expectations).
- **Existing operator/production write paths unchanged** — `PRODUCTION_ROLES` endpoints keep their exact behaviour so the ~40 production/consumption/material-state tests pass untouched.
- **`status` semantics unchanged** — still `PLANNED/IN_PROGRESS/COMPLETED/CANCELLED`; `stage` is parallel and additive.
- **Admin capture surface preserved** — all new models get Admin registrations consistent with existing ones; nothing existing is de-registered.
- **QC role widening is additive** — new `QC_ROLES` for QC records only; QC stays out of `PRODUCTION_ROLES`.

## 21. Existing-Data Risks

| Risk | Cause | Mitigation |
|---|---|---|
| Saving legacy runs breaks | `ProductionRun.save()` → `full_clean()`; new required fields would fail | Make all new run fields nullable; enforce completeness only in transition services |
| Historical consumption invalidated | Tightening `MaterialConsumption.batch/production_run` | Leave nullable; no changes to that model |
| Overwriting operator values | Naïve "auto-correct" | Engine only computes; corrections via audited service; originals preserved |
| Stage/status divergence | Two state fields | Mapping helper keeps them consistent for new runs; legacy `stage=null` |
| QC over-reach | Granting QC broad write | Scope QC to QC records; keep existing negative tests |
| Packaging cycles / bad config | Self-referential `contains` | `clean()` cycle + depth guard; base-pack invariants |
| Missing Pillow at QC step | `ImageField` needs Pillow (absent) | Use `FileField` (recommended) or explicitly add Pillow |
| Media not served in prod | Only served in `DEBUG` | Document prod media serving as a deployment note (out of V1.1 code scope) |
| Accidental drift fix | Running `makemigrations` broadly | Only generate migrations for the new apps/fields; never touch `accounts` |

New tests V1.1 must add (behaviour/structure, deterministic — no timing/pixel tests):

- **Catalog isolation:** product/variant/packaging are factory-scoped; cross-factory attach rejected.
- **Packaging relationships:** `individual_units` for 10's/15's/60's = 10/150/600; multi-level resolution; base-pack invariants.

- **Operator permissions:** operator can configure/start/output/submit-for-QC; operator cannot touch QC records (server-enforced, not just UI).

- **Supervisor permissions:** exception resolution and controlled corrections allowed; audit event created.
- **Photo ownership & upload:** photo tied to QC verification/factory/uploader; extension/size/content validation; rejection of bad files.
- **Expected quantity:** `20 × 15's = 3,000`; undefined when config incomplete.
- **Variance — recorded vs expected:** `3,400 vs 3,000 → +400`, correct percentage, `EXCEPTION` vs tolerance.
- **Variance — QC vs expected:** `3,000 vs 3,000 → 0`, `OK`.
- **Zero/negative/decimal quantities:** guarded; decimals to `0.001`.
- **Multiple runs / machines / historical runs:** isolation preserved; legacy compatibility.
- **Audit:** stage changes and corrections create events; originals preserved; append-only.
- **Regression:** full existing suite remains green; `makemigrations --check` shows only the pre-existing accounts drift.

## 23. UI Workflow Proposal

Extend the existing mobile-first, navy/steel operator workflow (`apps/dashboard/`), do not redesign unrelated UI.

Production → Select Product → Variant → Packaging → Line → Machine
          → Start Production → Record Output → Submit for QC

Supervisor/Admin:

- Exception queue (runs in `EXCEPTION`); correction dialog capturing old/new/reason; audit history view (WHO/WHAT/WHEN/OLD/NEW/WHY).

Accessibility/consistency: reuse existing components, `.input-control`, `.traffic` status dots, role navigation via `context_processors`. New nav entries gated by role.

## 24. API / Service Boundaries

Clear seams so the same logic serves UI now and AI later:

- `apps/catalog/services.py` — `individual_units(packaging)`, catalog lookups.
- `apps/production/variance.py` — `compute_variance(...)`, `variance_for_run(run)` (pure).
- `apps/production/state_machine.py` — `gate_requirements(run, target)`, `transition(run, target, *, actor)` (transactional, role-checked, audited).
- `apps/production/qc.py` (workflow) — QC verification create/update/complete, photo upload (role-checked).
- `apps/audit/services.py` — `record_event(...)`, `apply_controlled_correction(...)`.

Views/forms call these services; **no calculation logic in templates or views**. Services return structured, JSON-serialisable results.

## 25. Future AI Foreperson Integration Points (V2)

- **Variance engine** is the single source of production maths — the AI consumes `VarianceResult` rather than inventing calculations.
- **AuditEvent** stream is the factual history the AI reasons over (who changed what, why).
- **State machine + gate checker** expose "what is blocking this run" in structured form the AI can explain.
- **Packaging engine** gives the AI trustworthy pack↔unit conversions.
- All are pure/deterministic and factory-scoped, so AI outputs remain explainable and never become a source of truth (per architecture principle 3). No AI code in V1.1.
